Overview

Source: README.md

Spyglass is a command-line tool for coding agents and the people who review their work. It connects browser actions, HTTP calls, database reads and repository checks to one run. Each run records its source identity, every attempt (failed attempts too) and its artifacts. The evidence stays after cleanup, so another agent or person can inspect the result later without the original chat or shell.

An agent can say "the tests pass" or "the page works". That statement is not proof. Spyglass makes each verification step a recorded fact:

  • Real tools, no mocks. Spyglass drives a real browser, real HTTP requests, a real PostgreSQL database and the repository's own checks.
  • Evidence that stays. Screenshots, responses, query rows and logs go to a Git-ignored evidence folder with checksums. Cleanup does not remove them.
  • Honest results. Failed attempts stay in the record. A report stays incomplete until each claim has a completed step and its evidence.
  • Source identity. Each run records the commit and working-tree state. Evidence from source that changed after the run started cannot pass as proof for the original source.
  • Safe by default. The browser can open only the configured origins. Database queries run in a read-only transaction. Reports mask credentials, cookies and authorization headers.
  • Built for agents. Each command gives a versioned JSON result with --json, uses stable exit codes and never prompts.

Spyglass does not decide whether a claim covers the request, or whether a screenshot looks correct. The operator (the agent or person) selects the claims and judges the results. Spyglass makes sure that the cited steps completed, the artifacts exist, the source is current and the cleanup is done.

Install

Source: README.md

Requirements

  • Node.js 24 or later
  • Git

These tools are necessary only for some surfaces:

Tool Necessary for
agent-browser 0.38.2 up for a profile with a web origin. Browser checks (ui) also need its Chromium.
Docker Compose Container status and logs (ps, logs)
A PostgreSQL database Database reads (db). The driver is included.

Spyglass does not install tools, fetch secrets or start your app during init.

Install from source

Spyglass is not on npm yet. Install it from source:

git clone --branch v1.1.0 https://github.com/Schramm2/spyglass.git
cd spyglass
npm ci
npm run build
npm link
spyglass --version

Quickstart

Source: docs/quickstart.md

Use this disposable demo to learn the workflow that an agent uses. It starts a local HTTP app, records a failed assertion and a later passing check, and keeps its report after cleanup. It does not use paid services.

Prepare the demo

From the Spyglass checkout, copy the fixture and examples into a new temporary repository. Keep the printed directory for the trial. 

trial=$(mktemp -d /tmp/spyglass-trial.XXXXXX)
mkdir -p "$trial/fixtures"
cp -R fixtures/demo-app "$trial/fixtures/"
cp examples/demo.profile.json "$trial/spyglass.json"
cp examples/demo.plan.json "$trial/verification-plan.json"
printf '.spyglass/\n' > "$trial/.gitignore"
cd "$trial"
git init -q
git add .
git -c user.name='Spyglass Trial' -c user.email='trial@example.invalid' commit -qm 'Demo baseline'
printf '%s\n' "$trial"

Start, fail and check

spyglass up --run terminal-trial --plan verification-plan.json
spyglass check deliberate-failure --run terminal-trial
spyglass check health --run terminal-trial
spyglass status --run terminal-trial

The deliberate check must exit 1 with CHECK_FAILED. The health check must exit 0 and show health-ready: true. Both attempts stay in .spyglass/runs/terminal-trial/spyglass/log.jsonl. Each output names its step. The health output also names its artifact.

Record what you observed

The step log records what happened. The result file records what it proves: for each claim, you name the steps and artifacts that prove it. result checks that those steps completed and that the artifacts exist with their checksums, so a claim cannot pass on a statement alone. An agent normally writes this file; in this trial, you write it.

Open .spyglass/runs/terminal-trial/spyglass/result.json in your editor. Set operator to human. For health-ready, set outcome to passed, copy the health step ID into steps, and copy its artifact path into artifacts. Write your observation in observed.

Fill the prepared failure-detection entry in the top-level controls array. Use the two step IDs from the failed and passing commands: 

{
  "id": "failure-detection",
  "failedStep": "FAILED_STEP_ID",
  "restoredStep": "HEALTH_STEP_ID",
  "observedFailure": "The deliberate check failed health-ready.",
  "observedPass": "The health response returned HTTP 200 and status ok."
}

Keep the existing limits. This result proves the health command and the failed assertion check. It does not prove a UI or persistent data. 

spyglass result --run terminal-trial --file .spyglass/runs/terminal-trial/spyglass/result.json
spyglass doctor --run terminal-trial
spyglass down --run terminal-trial
spyglass report --run terminal-trial

Open the page at reportPath in the report output. Check that it includes both attempts, the observation, the source identity, the limit and cleanup. A report run before cleanup must remain incomplete. Running report after cleanup needs no live app.

Continue an agent's run

In a prepared trial, an agent has started the run agent-handoff, recorded one check and left the run idle. Continue it without the agent's chat or shell: 

spyglass status --run agent-handoff

Use the status output to find the completed check, its outcome and the pending claim. Run the check that the claim still needs, record the result as in "Record what you observed", then run down and report for agent-handoff. If another operator is driving the run, Spyglass refuses your command with RUN_BUSY; wait until that command finishes.

Handoff

Open a new terminal, change to the printed trial directory, and run: 

spyglass status --run terminal-trial
spyglass report --run terminal-trial --json

The run should remain stopped and its report should still be complete. A person or agent can inspect it without the original shell or chat. Record any unclear step or missing information as a usability defect.

Workflow

Source: README.md

In your own repository, the workflow is:

spyglass init                                   # write spyglass.json; review it
spyglass up --run my-change --plan verification-plan.json --json
spyglass check verify --run my-change --json    # run a named check
spyglass result --run my-change --file PATH     # record claim results
spyglass doctor --run my-change --json
spyglass down --run my-change --json            # clean up owned resources
spyglass report --run my-change --json          # write the offline report

Add .spyglass/ to your .gitignore. It holds the evidence folder.

up --plan writes a pending result file and prints its path. Put the step IDs, artifact paths and observations from your checks into that file. Then record it with spyglass result. If a check fails, keep the original expectation. Repair the source and start a new run.

Concepts

Source: GLOSSARY.md

These terms name the parts of a verification, from the repository setup to the retained report.

Runs and evidence

Run
One verification with a fixed source identity and isolated resources. Avoid: session (a browser session belongs to a seat inside a run)
Step
One recorded CLI operation within a run, including a failed one.
Attempt
One execution of a check. Failed attempts stay in the record.
Artifact
A retained file tied to the step that produced it and to its source identity.
Evidence folder
A Git-ignored directory in the target repository that holds a run's step log, artifacts and report, and survives cleanup.
Source identity
The commit and working-tree state that a run records when it starts. Evidence from changed source cannot prove a claim about the recorded source. Avoid: snapshot (ui snapshot captures the page state)
Import root
A directory that a profile declares as a safe origin for imported artifacts.
Mark
A named timestamp in a run that later log reads start from.
Report
The offline record of a run: its claims, steps, artifacts, controls, limits and cleanup. It stays incomplete until each required claim has its proof.

Plans and results

Plan
The claims, controls, gates and limits that a run must cover, fixed when the run starts.
Claim
An observable acceptance condition, with its entry point, precondition, expected result and the checks that supply its evidence.
Result
The operator's record of the outcome and evidence of each claim, control and gate in a plan.
Control
A deliberate failing attempt and its restored passing attempt, which show that a check detects the failure it is meant to detect.
Gate
A repository-required check named in the plan. The result records its outcome and the steps that prove it.
Limit
A stated part of the behavior that a run's evidence does not cover.
Independent read
A step after a side effect completes that reads the result through a separate path, such as a database read after an API write.
Inspection
The operator's record of what a screenshot shows at a stated viewport, compared with the expected appearance.

Repository setup

Profile
The configuration of one target repository: tools, commands, bindings, seats, checks and evidence rules.
Lifecycle mode
The rule for who starts and stops the target app: owned (Spyglass), external (the repository's own tool) or none (no persistent target).
Owner
The repository's own tool that starts, checks or cleans up its resources when the lifecycle mode is external.
Binding
A named value that fills a placeholder in a profile for one run, such as a port or an installation name.
Seat
A named test identity with credential references.
Check
A named, repeatable command or journey in a profile that supplies evidence. Avoid: test (a test is one kind of check)
Surface
A kind of target that Spyglass can drive or observe: repository checks, commands, the browser, HTTP, PostgreSQL, Docker Compose and imported evidence.
Adapter
The part of Spyglass that connects one tool to a surface and to the run and evidence contracts.
Adapter gap
A required behavior that works for a user but that no adapter can drive or observe.

People

Operator
The agent or person who selects claims, drives the run and judges the results.

Commands

Source: src/help.ts, src/cli.ts, src/browser.ts

The options are --json and --help. Run selection is --run ID or SPYGLASS_RUN. Run spyglass --help for all commands, and spyglass COMMAND --help for one command.

Exit codes: 0 success; 1 failed verification; 2 invalid input; 3 environment failure. A successful command is evidence for a step. It does not by itself prove a claim.

init

spyglass init [--force]

Read repository verification guidance and task runners. Write spyglass.json with observed and guessed fields. Review owner setup, guessed readiness and addresses before up. No app starts. --force prints changed fields before replacement. 

spyglass init --json

up

spyglass up [--run ID] [--profile PATH] [--binding NAME=VALUE] [--plan FILE]

Create a run with a fixed source baseline and a pending result template. Evidence must be Git-ignored and unique to the run. owned starts an app; external calls its owner doctor without starting owner resources; none runs checks without a server. Bind only non-secret values. Secret fields use env:, file:, dotenv:path#KEY or op:// references. Direct launch: up --cmd "npm run dev" --ready http://127.0.0.1:3000. Explore without a plan; a complete report requires claims. 

spyglass up --run change-42 --profile spyglass.json --plan verification-plan.json --binding ownerRun=example --json

status

spyglass status [--run ID]

List the runs of every worktree of the repository, or inspect one run: source, active command, completed checks, pending claims, capabilities, owner resources, cleanup and the next command. Inspection works while another operator drives the run. completedChecks names childExitCode (child process) and spyglassExitCode (Spyglass command); exitCode and commandExitCode remain aliases. A run whose worktree was removed shows worktreeRemoved; stop it with down from any worktree. 

spyglass status --run change-42 --json

doctor

spyglass doctor --run ID

Check immutable source, readiness and the configured owner doctor. Database profiles report role permissions when credentials are available. A writable role is a limit: read-only transactions cannot prevent every function side effect. Diagnostics retain their evidence; a source mismatch never resets the baseline. 

spyglass doctor --run change-42 --json

down

spyglass down --run ID

Stop only the run-owned app process group and browser sessions. Keep evidence and run records. For external resources, run the profile check with cleanup:true through the owner before the final report. Repeated down is safe. 

spyglass down --run change-42 --json

check

spyglass check NAME --run ID

Run a profile command with its bindings, environment and deadline. result:exit checks the child exit; result:json requires nonempty valid assertions; result:engine imports the owner journey result. Failed assertions, skips and artifact errors remain failures even when the child exits zero. Declared artifacts must be in allowed import roots. cleanup:true records successful owner cleanup. 

spyglass check verify --run change-42 --json

exec

spyglass exec [--timeout-ms MILLISECONDS] --run ID -- COMMAND [ARGUMENTS]

Run a trusted command as separate arguments and retain output. The default deadline is 300 seconds; --timeout-ms selects an integer from 1 to 86400000 milliseconds. The output limit is 8 MiB. data.exitCode retains the child status; the CLI exits 1 for a failed child. Global options go before --. exec is not a sandbox and command success alone proves only its declared command-level condition. 

spyglass exec --run change-42 --json -- npm test

api

spyglass api METHOD PATH --run ID [--seat NAME] [--data JSON|@FILE] [--expect STATUS]

Request a path relative to profile.api. A named seat resolves its token reference privately. Requests stay on the configured origin; redirects are retained but not followed. Invalid JSON is rejected before sending. Save the masked request and response, print a short body, and compare --expect when given. HTTP 202 means accepted, not completed: wait for completion and then make a separate read. Keep raw credentials out of argv. 

spyglass api GET /jobs/123 --run change-42 --seat member --expect 200 --json

db

spyglass db SQL --run ID [--expect-rows N]

Run one PostgreSQL statement through the extended protocol in a read-only transaction. profile.db.connection must be a secret reference. Retained results are bounded to 1,000 rows and 1 MiB; overflow is a failed check. No psql meta-commands. Role warnings describe remaining function-side-effect limits. Use the owner database; this command creates no server. 

spyglass db "SELECT 42 AS answer" --run change-42 --expect-rows 1 --json

ps

spyglass ps --run ID

Inspect only profile.compose.project with its declared files. Print container state and health. A required service that is not running fails; this command changes no container. 

spyglass ps --run change-42 --json

mark

spyglass mark LABEL --run ID

Save a timestamp in this run for later process or Compose log inspection. 

spyglass mark before-action --run change-42 --json

logs

spyglass logs [SERVICE] --since MARK --run ID

Read retained app logs or the declared Compose project since an existing mark. Save masked evidence. Missing marks fail and list the known marks. Diagnostics remain available after a drive fails. 

spyglass logs app --since before-action --run change-42 --json

evidence

spyglass evidence add --step STEP_ID --file PATH --run ID

Copy a regular file from the evidence folder or a profile.imports root. Retain its checksum and producing-step reference. Original files remain unchanged. Reject unsafe paths, symlinks and unsupported formats. Use named-check artifact declarations for normal check output. 

spyglass evidence add --step 123456 --file runs/owner/result.json --run change-42 --json

result

spyglass result --file PATH --run ID

Read the edited result template printed by up. Validate claim IDs, cited steps and artifacts, visual inspection, independent reads, gates and predeclared negative controls. For multiple viewports use inspections with viewport, expected, observed and artifact for each cited screenshot. The single inspection remains supported. Controls include failedRun; replace its current run ID when the failure belongs to an earlier run, also one from another worktree of the repository. Keep that worktree until the report. A gate can name run, another run with the same source identity, profile and bindings whose steps prove it. Use spyglass schema result for the full shape. Recording a result does not complete cleanup or certify semantic coverage. 

spyglass result --file .spyglass/runs/change-42/spyglass/result.json --run change-42 --json

report

spyglass report --run ID

Write retained offline HTML and JSON from the run log, recorded result, source and artifact checksums. Only a result recorded with spyglass result counts. data.reportPath is the absolute path of the HTML page. Works after cleanup without contacting the app. Missing claims, controls, required gates, cleanup, altered evidence or source changes produce a diagnostic report and exit 1. Prior failed attempts remain visible. 

spyglass report --run change-42 --json

schema

spyglass schema profile|plan|result

Print the version 1 JSON schema without a repository or run. --json wraps it in the standard result envelope. 

spyglass schema profile --json

ui

spyglass ui [--seat SEAT] <agent-browser command>

Drive the web browser of a run. Each run and seat gets a new headless browser session. Spyglass uses an explicit config and allowed run origins. Page output is marked as untrusted content. Run spyglass ui --help for all operations and limits.

Evidence: an isolated session, screenshot, DOM, errors and requests. Operations include:

  • open PATH|URL
  • read [PATH|URL]
  • snapshot [-i|-c|--delta|--full]
  • proof LABEL
  • focused [--expect LABEL]: records the focused element's role, label, type and ID without its value. --expect fails when the label differs.
  • login SEAT
  • screenshot PATH
  • console, errors, network requests

Use spyglass down to close run-owned sessions. A seat browser left idle for browser.idleTimeoutMs (default 1 hour) shuts down. The next ui command reports BROWSER_EXPIRED. 

spyglass ui open / --run change-42

Surfaces

Source: README.md

A surface is a kind of target that Spyglass can drive or observe. Version 1 supports these surfaces:

Surface Commands Evidence
Existing tests and journeys check NAME Exit status, assertions, declared artifacts
Other commands exec -- COMMAND ARGS Bounded stdout and stderr, real exit status
Web browser ui open /, ui snapshot, ui proof LABEL, ui focused Isolated session, screenshot, DOM, errors and requests
HTTP api GET /path --expect 200 Masked request and response; redirects are not followed
PostgreSQL db 'SELECT ...' --expect-rows 1 One statement in a read-only transaction, with rows and role limits
Docker Compose ps, mark LABEL, logs SERVICE --since LABEL Project-scoped status and timestamped logs
Other evidence evidence add --step ID --file PATH Checked copy from a declared import root

Run spyglass --help for all commands, and spyglass COMMAND --help for the arguments of one command.

Configuration

Source: README.md

spyglass init writes a profile (spyglass.json). It contains the tools, commands, bindings and evidence rules for one repository. Review the guessed fields before you run up. See the example profile and the example plan.

The JSON schemas are in schemas/. You can also print them: 

spyglass schema profile
spyglass schema plan
spyglass schema result

Lifecycle modes

A profile selects one lifecycle mode:

Mode Who starts and stops the app
owned Spyglass starts a process group and stops it on down.
external The repository's own tool starts and stops its resources. Spyglass records its doctor and checks. A named check with cleanup: true records the owner's cleanup. down closes only the Spyglass browser.
none There is no persistent target, for example a library journey.

For a long command, use spyglass exec --timeout-ms 900000 --run ID -- COMMAND. The default is 300 seconds; the maximum is 24 hours. The selected deadline is retained with the result. CLI binding overrides are retained with their resolved values, including bindings added only on the command line.

Credentials

Do not put credential values in a profile. Use references:

  • env:NAME
  • file:path
  • dotenv:path#KEY
  • op://vault/item/field (1Password CLI)

A seat is a named test identity with credential references. Screenshots can contain private data. Examine the page state before you take one.

Plans and results

Source: README.md

up --plan writes a pending result file and prints its path. Record the edited file with spyglass result.

Inspections

A visual result can use inspections, with one entry per viewport. Each entry has viewport, expected, observed and artifact; the artifact must be a valid screenshot from a cited step. The earlier single inspection remains supported.

Controls

Control templates include failedRun, initially the current run; replace it when the intended failure belongs to a retained earlier run.

Worktrees

All worktrees of a repository share their runs. Put a fault in a separate worktree, record its failing run there, and name that run in failedRun. Run down for the fault run in its own worktree; Spyglass refuses commands that change a run from another worktree (RUN_OTHER_WORKTREE). Keep the fault worktree until the candidate report: its evidence folder holds the failed attempt. Run IDs are unique in the repository. If a worktree is removed while its run is active, status shows worktreeRemoved and down stops that run from any worktree.

Gates

A gate can cite another run with run, for example one run that executes the repository gates for several journeys. Its steps must have passed on the same source identity, profile and bindings as the run that records the result.

Output and exit codes

Source: README.md

Default output is compact, indented text for people. --json gives one versioned result object on stdout and diagnostics on stderr. The two modes use the same handler and the same exit code.

Exit code Meaning
0 Success
1 Failed verification
2 Incorrect input
3 Environment failure

--run ID selects a run across shell calls. You can also set SPYGLASS_RUN; --run has priority. spyglass status --run ID shows the handoff state of a run. completedChecks.childExitCode is the child process exit code; completedChecks.spyglassExitCode is the Spyglass command exit code. A child can exit zero while Spyglass rejects failed assertions. The earlier exitCode and commandExitCode fields remain as aliases.

Failure cases

Source: docs/failure-cases.md

These cases define failures that the public CLI must detect. The end-to-end tests run the built CLI in temporary Git repositories. They test observable results and retained evidence.

Area Failure case Required result
Input The profile has an unsupported version or an unknown field. The command exits with usage/profile status and names the invalid field. It does not launch the app.
Setup Two profiles match the repository. The command asks for an explicit profile through an error and next action. It does not prompt.
Setup A CLI binding overrides a profile default. Execution and retained binding records use the same resolved override.
Command A command exceeds its selected deadline. The attempt retains timeout status and output; an invalid deadline is rejected before execution.
Run The app exits before its readiness check succeeds. The run remains recorded as failed, its ID is returned, and status and cleanup remain available.
Run Two operators try to change one run at once. One mutation owns the lock. Status can inspect the active command. The second mutation fails with a recovery action.
Source Source changes after the run starts. Later evidence cannot be presented as proof for the original source. The run records both source identities or rejects the stale result.
Check A check exits zero but reports a failed assertion or skipped required assertion. The check fails and retains the command result, assertion details, skips, and artifacts.
Claim A required claim has no completed step or required evidence. The claim cannot pass. The report stays incomplete and names the missing proof.
Claim A side-effect claim has no independent read after the action completes. The claim cannot pass.
Evidence An imported artifact is missing, outside an approved root, or changes during import. The import fails and does not claim the artifact as evidence.
Secret A request or page reflects a test credential. Reports and artifacts do not expose credential values, cookies, or authorization headers.
Browser A browser action targets an origin outside the profile allowlist. The action fails with the required capability or policy named. It does not use another browser session.
Browser A screenshot succeeds but a visual claim has no inspection record. The visual claim remains incomplete.
Browser An inspection for a viewport names a missing or unrelated screenshot. The result fails and names the inspection's missing proof.
Operator A child exits zero but its assertions fail. Status names the child and Spyglass exit codes separately. Default output is readable text.
Output External output contains terminal controls or a new line that resembles a Spyglass field. Text output escapes the control bytes and keeps external content inside its field.
Compatibility A version 1 result has a single inspection and no inspections array. Both the CLI and the published schema accept the result.
Control A control needs a failure from an earlier run. The result template includes the failed run ID, which the operator can replace with the retained baseline run.
Control The failed attempt ran in a separate worktree of the same repository, for an isolated fault. The candidate's result finds the failed run by its ID. A command that changes a run from another worktree fails and names the run's worktree. If that worktree's evidence was removed, the control fails and names the missing folder.
Gate A result cites a gate that passed in another run. The gate counts only when its steps passed on this run's source identity. Otherwise the result fails and names the source mismatch.
Gate A cited gate step used a binding override whose value differs from this run's: a named check against another database or API, or any step against an app that Spyglass launched with another setting. The result fails and names the binding. A binding that the step did not use, such as an external installation's own port beside an exec gate, does not block the gate.
Browser A claim needs to know which element has focus. ui focused records the focused element's role, label and type without its value. --expect LABEL fails when the label differs.
HTTP A request returns an unexpected status or an asynchronous submission is checked before completion. The expected-status check fails, or the workflow waits for completion before an independent read.
Database A query attempts to write data. Spyglass rejects it before execution.
Database A query contains multiple statements, attempts to escape its transaction, or contains a psql meta-command. PostgreSQL's extended protocol rejects multiple statements. Client meta-commands never run. No side effect occurs.
Database A query returns more rows or encoded output than the supported bound. The query fails with a clear limit and does not retain an unbounded result.
Database A query returns a different row count than --expect-rows. The command fails and retains the observed count and bounded result.
Containers A run stops. Spyglass stops its own processes and browser. The repository owner cleans its containers; shared services and evidence remain.
Report The operator edits the result file but does not record it with result. The report ignores the unrecorded file, stays incomplete with RESULT_MISSING, and status names result as the next command until a result is recorded.
Report Required work or owner cleanup is missing. The report files are still produced, but the run is incomplete and exits with failed-check status.
Operator A required input is missing while JSON mode is active. Stdout contains one versioned result object, stderr contains diagnostics, and the command exits without prompting.

Codes in the output

These codes appear in command output and in the report for the most common failures. The CLI source in src/ defines them.

Code Failure
STALE_SOURCE Source changes after the run starts.
CHECK_FAILED A check exits zero but reports a failed assertion.
CLAIM_INCOMPLETE A required claim has no completed step.
INDEPENDENT_READ_MISSING A side effect has no independent read after it completes.
BROWSER_ORIGIN_BLOCKED An action targets an origin outside the allowlist.
VISUAL_INSPECTION_MISSING A screenshot exists but nobody inspected it.
API_EXPECTATION_FAILED A request returns an unexpected status.
DATABASE_READ_ONLY A query tries to write data.
DATABASE_ROW_COUNT A query returns a different row count than expected.
RUN_BUSY Two operators change one run at once.
CLEANUP_PENDING Cleanup did not happen.

Agent skills

The skills/ directory holds the agent skills for Spyglass. They use the Agent Skills format.

Skill Purpose

create-verification-skill Create a repository's own verify-<app> skill.
maintain-verification-skill Keep that skill current as the app changes.

Copy a skill folder into the skills directory of your agent harness, for example .claude/skills/ or .agents/skills/.

Limitations

Source: README.md, docs/browser-benchmark.md

  • Version 1 supports the surfaces in the Surfaces table. It has no native desktop, mobile or TUI driver. For those, use the repository's own checks and import their evidence.
  • The browser accepts only the configured origins.
  • Read-only database mode is not a sandbox for privileged functions. Use a restricted database role.
  • An HTTP 202 response does not prove that background work finished. Wait for completion, then do an independent read.
  • A run's browser stops after browser.idleTimeoutMs with no ui command (default: 1 hour). The next ui command reports BROWSER_EXPIRED, and a seat must sign in again. Run down when your checks are complete.

See failure cases for the failures that the CLI must detect. See browser overhead for the measured cost of browser commands. The budget is 150 ms added at the median. Measured on 2026-10-22, the median added time was 91.7 ms.
